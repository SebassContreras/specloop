- [x] T021 [agent] [status:done] Recover a task stuck `in_progress` from an ungraceful external kill (not `safeStop`'s clean path) — `nextRunnableTask` currently only resumes `todo`/`interrupted`, so such a task blocks its spec forever without a manual reset
      └─ Found during `006` T010's live run: the invoking shell's own command timeout (not the orchestrator's 30-min `WORKER_TIMEOUT_MS`) killed a `claude -p` call mid-task, leaving it `in_progress`; recovered by hand.
      └─ Fixed with a per-task PID registry (`src/taskLock.ts`, new): whichever process actually blocks on a task's worker — the master itself under `splitMode: "none"`, or the detached pane's own process under `windowsTerminal`/`tmux` (`runTask`, not the master, which moves on immediately) — registers its own PID before starting the task and clears it on completion. Chosen over a single run-wide lock because a global lock can't tell a live detached-pane task from a dead master: the master returns as soon as it dispatches a split-pane task, so its own lifetime doesn't bracket "is the work still happening" the way a per-task PID does. Before giving up on a spec with no `todo`/`interrupted` task, `run()` now checks any `in_progress` task's registered PID (`process.kill(pid, 0)` — a portable liveness probe on both POSIX and Windows): alive means genuinely still running (left alone); dead or missing means recovered to `interrupted` and retried in the same call.
      └─ Verified live: reproduced the exact scenario in `test/architecture-absent-fixture/` — manually reset an already-`done` task to `in_progress` with no registered PID (simulating the ungraceful kill) and reran `loop run`. Output: `[loop] recovered 1 task(s) left in_progress by a process that's gone: T006`, then it re-dispatched T006 to a real `claude -p` worker, which independently re-verified the already-correct prior work and closed it back out. `pnpm exec tsc --noEmit` / `pnpm exec eslint src` clean; a standalone script also confirmed `isTaskStillRunning` correctly reads never-registered, live-PID, dead-PID and cleared states.
      └─ **Follow-up bug found and fixed same session, during `006` T012's `windowsTerminal` test**: the recovery check originally ran on *every* iteration of `run()`'s dispatch loop, not once. Under a detached split-pane, the master writes `in_progress` and moves on immediately (never blocks), so the very next loop iteration re-checked the task it had just dispatched — before the detached pane had any chance to register its own PID — read it as already-dead, and re-dispatched it. That repeated every iteration, spawning a fresh `wt split-pane` window each time: 13 iterations, 9 real stray `cmd` windows each running a real `claude -p` call, until one finally won the race and the loop stopped. `splitMode: "none"` was never affected (synchronous, no such gap). Fixed by moving the recovery sweep (`recoverStaleTasks`) to run exactly once, before `run()`'s dispatch loop starts — anything already `in_progress` at that moment necessarily predates this invocation, so it's safe to judge; a task *this* call dispatches is never re-examined within the same call. Stray windows closed by hand; re-verified the fix stops the runaway spawning (a repeat run recovered the task exactly once, not repeatedly).

- [x] T022 [agent] [status:done] Stream a worker's stdout/stderr live to whichever terminal is running it, instead of buffering the whole run and only writing the log once it exits
      └─ Found during `006` T012's live `windowsTerminal` test: the user watched the split-pane and, correctly, expected to see the agent working — instead the pane printed "running task X" once and went silent until the whole task finished, because `worker.ts` used `spawnSync` with piped stdio (captured into a buffer, written to the log only on exit).       └─ Fixed: `runWorkerSync` (`spawnSync`) replaced with `runWorker` (async `spawn`), relaying each stdout/stderr chunk to this process's own stdout/stderr *as it arrives* while also accumulating it for the persisted `.log` file — one stream, two destinations, no behavior change to the worker CLI itself (same prompt, same call, same cost — purely how the parent process reads the same output). Verified with a fast dummy worker (`node -e` writing two chunks 300ms apart): both chunks printed to this process's stdout *between* the call's start and its return, not after — confirms real streaming, not another buffered write in disguise. `pnpm exec tsc --noEmit` / `pnpm exec eslint src` clean.
