## Code conventions

Researched via web search 2026-09-14, not invented (see `.specloop/interview.md`).

- **Naming**: kebab-case for files and directories (`skills/loop-setup`,
  `planning/specs/026-dashboard-visual-enhancements`), with the standard
  exception for root entry-points (`README.md`, `AGENTS.md`, `CLAUDE.md`,
  `LICENSE`) — already this repo's practice, confirmed as the current
  industry default.
- **Comments**: minimal — explain *why*, not *what*. Matches
  `scripts/check-skill-consistency.mjs`'s own header comment and every
  `SKILL.md`'s "terse and structural, no filler prose" rule.
- **Commit messages**: **Conventional Commits**, `<type>(<scope>):
  <description>`, description in imperative mood (`add`, not `added`) —
  `type` ∈ `feat` / `fix` / `docs` / `chore` / `refactor` / `test` / `build` /
  `ci`; `scope` is the skill name or spec ID where one applies (e.g.
  `fix(loop-setup): known CLI flags`, `docs(roadmap): update 026 stage`).
  **This changes going forward, from this date — does not rewrite this
  repo's existing history**, which predates this convention and used plain
  imperative subjects with no type prefix.
- **Scripts**: ESM (`.mjs`), no build step — matches
  `scripts/check-skill-consistency.mjs`, the only script in the repo today.
- **Markdown headings**: sentence case (capitalize only the first word and
  proper nouns) — `## Who/what it serves`, not `## Who/What It Serves`.
  Already this repo's de facto practice; now explicit.
- **A canonical header, once defined, is never paraphrased.** Downstream
  tooling (`design-closing`, `task-breakdown`, the parsers in `skills/loop`/
  `skills/status`) matches literal header text — `## Out of scope`, never
  `## Scope`/`## Non-goals`. See `planning/architecture.md`'s Fixed rules
  for the collected canonical header sets.
- **Each section is one complete, independently retrievable idea** — a
  reader (human or agent) pulling just that section, without the ones
  around it, should never be missing context it needed. Researched
  2026-09-14 (the `llms.txt`/`AGENTS.md` conventions, LLM-context chunking
  practice): the same shape this repo's canonical requirements/design/tasks
  templates already follow.
- **Don't restate what another file already owns.** `planning/roadmap.md`
  owns `Status`/`Stage`/`Priority`; a spec's own files reference it, never
  re-derive or duplicate its values in prose.

## Tone

Technical and direct. English. Matches the existing style already visible
across every `SKILL.md`/`planning/*.md` in this repo ("terse and structural,
no filler prose, no marketing language").

`language` field: **omitted** from `.specloop/loop.config.json` — English is
the no-field default per `planning/architecture.md`'s Fixed rule
(`fix/001-language-field-format`).

## Anti-preferences

1. Filler / marketing / hedging prose — anything that isn't terse and
   structural, consistent with the rest of the repo.
2. Config, columns, or skills added "just in case," with no concrete, current
   need behind them.
3. A rule, doc, or skill that claims a behavior the code doesn't actually
   implement.
4. A guessed technical value (a flag, a format) presented without verifying
   it first.
5. A proposed command or feature that isn't actually mechanically possible
   given how this repo is built (e.g. "changing the master" from inside a
   session, when the master is whichever harness the user actually
   launched).

## Preference strength

**Hard rule — every preference above, no exceptions.** Palette/typography/
density, code conventions, tone/language, and every anti-preference: none is
a default an agent may deviate from with reason. Confirmed explicitly
2026-09-14: "hard rule everything, default nothing."
